# Provider Comparison — Multi-Tool Survey

A side-by-side quality survey of four text-to-pixel-art providers on the same
prompts and asset types. Companion to the main paper (*Godot Asset Generator —
Workflow and Provider Comparison*), which deep-dives the **native vs. downscale**
mechanism between PixelLab and OpenAI. Here the question is wider and simpler:
**given the same request, which tool produces the more usable game asset?**

PixelLab and OpenAI are **not regenerated** — their images are reused from the
main paper as a reference line. Meowa and FrameRonin are generated by us, on
their own websites.

> **On FrameRonin's fourth column.** FrameRonin is not a turnkey generator: it is
> a front-end over an external model (`nano-banana` = Google's Gemini image
> model), gated behind a bring-your-own API key. Two consequences for fairness,
> both labeled on its cells: (1) generation runs through FrameRonin's **preset**
> generators, which inject their own engineered prompt — so it is *not* the same
> prompt as the other columns; (2) output is **1k, then downscaled** — not native
> pixels, like OpenAI. Read the column as "FrameRonin the product," not as the
> same-prompt control the other columns form.

## 2. Method

- **Self-generated, not gallery images.** Every image is generated with
  our own prompt.
- **Same prompt per row.** Only the provider changes across a row; the asset and
  prompt are held fixed (same prompts as the main paper — filled in §2.1).
- **Default web UI.** New providers are generated through their website with
  default settings, at (or nearest to) the target size. The generation method is
  recorded, since a web UI may apply its own post-processing (auto-downscale,
  palette cleanup, background removal) that an API would not.
- **Display.** Baseline images are shown upscaled ×8 (nearest-neighbor) for
  legibility, as in the main paper. Show the new-provider images at a comparable
  on-screen size.

## 4. Observations

_To fill after generating. Per provider, note: prompt understanding, pixel
cleanliness (clean palette vs. AI in-between colors), size ceiling / native
support, and whether the web UI does its own post-processing._

- **Meowa** — Two generation modes that split exactly along this paper's native
  vs. downscale line:
  - **Template mode (模板生成)** lets you set a true pixel size (16 px, 32 px …),
    so it outputs *native* small pixels — like PixelLab. The template thumbnail
    (a set of minimalist icons) is only a preview; the prompt still drives the
    output. The tile prompt returned a **batch of 36 distinct 16×16 stone-floor
    tiles** in one job (see appendix) — effectively a free tileset, and a genuine
    strength for the tile row: native size plus many variations at once. Its size
    grid is fine — 16 / 24 / 32 all native, including the production 24 px — so it
    is not stuck on powers of two the way many pixel tools are.
  - **Universal mode (万能生成)** takes a free prompt but exposes only an *aspect
    ratio*, not a pixel size — it renders a large image you must downscale
    yourself, like OpenAI. It also offers no 1:1 ratio, which is awkward for a
    square tile. Better suited to the character and scene rows.
  - **Icons behave like tiles.** The healing-potion icon prompt in template mode
    returned **15 native 24×24 icons** in one job (round, heart, star, test-tube,
    jar variants), each with a real transparent background and clean hard pixels
    — a ready icon set at the exact production size, no downscale.
  - *Recording rule:* label each Meowa image with the mode used, since template
    mode is native and universal mode is a downscale (not comparable as-is).
- **FrameRonin** — The least self-contained of the four. It hosts no model of
  its own; it is a front-end that drives an external image API, defaulting to
  `nano-banana` (Google's Gemini image model). Practical findings:
  - **No free/turnkey path.** Every generation requires an API key. The
    "non-API preset" banner is misleading — clicking generate still demands a
    key. Direct Google (AI Studio) config failed because the tool expects a relay
    alias (`nano-banana-fast`), not Google's native model/host; usable output
    effectively depends on a paid third-party relay.
  - **Value-add is presets, not the model.** Its strength over raw nano-banana is
    a library of **engineered preset generators** (pixel character V2–V3, monster,
    scene with front/45°/arcade views, 8-direction, full-body action) plus a
    pixel post-pipeline (sprite-sheet split/merge, background cutout, tile
    adjust). These inject hidden designed prompts — which is exactly why using a
    preset breaks the same-prompt control.
  - **Not native pixels.** The preset dialog exposes an aspect ratio and a **1k**
    resolution, so like OpenAI it renders high-res and must be downscaled to the
    target size. The character preset (V2) returned a full animation sheet of a
    green-armored *soldier*, not the requested knight — the preset's own prompt
    overrode the description. At 1k the sprite is detailed, but downscaled to
    32×32 it collapses into a muddy blob, the same native-vs-downscale failure as
    OpenAI at small sizes, and a sharp contrast with Meowa's crisp native 32.
  - **Scene preset has no top-down view.** Its scene generator offers only
    front / 45° / Terraria / arcade views — all side or isometric. A top-down
    scene had to be made through free-gen with our overhead prompt, bypassing the
    preset entirely.
  - **Tile prompt was misread.** Free-gen read "stone floor tile" literally as a
    full **grouted tiled floor** (an 8×8 grid), not a single seamless swatch — and
    a grid with grout cannot repeat as a tile. The other three providers returned
    a single tileable motif from the same prompt. This shows the raw model needs
    strong negative constraints (no grid lines / borders / seams, as the main
    paper's ground_atlas prompt carries) where PixelLab and Meowa give a usable
    single tile natively. One cell was cropped out for the grid cell.
  - **Icon isn't pixel art, and the transparency is fake.** The same icon prompt
    returned a **1024×1024 smooth vector-style potion** — anti-aliased, gradient-
    shaded, not a pixel grid. Worse, its "transparent" background is a **painted
    light-gray/white checkerboard** baked into an RGB image (no alpha channel), so
    it would have to be keyed out before use in-engine. Downscaled to 24×24 it
    collapses into an anti-aliased blob, the same failure as its 32 px character —
    while Meowa gives a crisp native 24 with real alpha.
  - *Recording rule:* the FrameRonin column is the *product* (preset or free-gen
    + 1k downscale), not the same-prompt / native control the other columns form.

## 5. Verdict

- **Meowa** — Worth adopting, especially for tiles, characters, and icons.
  Turnkey (no setup), it generates *native* small sizes across a fine grid —
  16 / 24 / 32, including the production 24 px — and returns a whole batch of
  variations per job (36 tiles, 15 icons), making it the most productive of the
  new tools. Its universal mode covers scenes OpenAI-style; the only real limit
  is scene aspect ratio (no 16:9, 3:2 closest).
- **FrameRonin** — Not worth adopting for this pipeline. It is a
  bring-your-own-key client over nano-banana with no turnkey path (needs a paid
  relay); its presets override the prompt (a soldier, not the requested knight)
  and offer no top-down scene view; and its 1k → downscale output collapses at
  small sizes — the 32 px character became a muddy blob, and the 24 px icon came
  back as a smooth vector potion with a fake painted-checkerboard background —
  while free-gen misread the tile prompt as a grouted floor grid. A capable model
  at large sizes, but a poor fit for native small tiles, characters, and icons.
  Niche at best.
- **Overall** — For the sizes that matter here (16 / 24 / 32 px), the
  pixel-*native* tools (PixelLab, Meowa) beat the high-res-render-then-downscale
  tools (OpenAI, FrameRonin / nano-banana). This reaffirms the main paper's
  native-vs-downscale thesis across two more providers.
